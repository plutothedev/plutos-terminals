# v0.1.29 — scrollback survives tray→Quit + reboot

The big one. Fixes the bug where panes came back on the next launch with the right project / cwd but the **text and stuff that was in the pane** was gone.

## What was wrong

Scrollback persistence was written in the React component's unmount cleanup function (`TerminalPane.jsx` line 615):

```js
return () => {
  ...
  invoke("scrollback_save", { tabId: id, content: tail }).catch(() => {});
  ...
};
```

That fires reliably when a tab is closed during normal use. It does NOT fire reliably on tray → Quit, because:

1. `app.exit(0)` in Rust fires `RunEvent::ExitRequested` → `pty::kill_all()` → process exits.
2. React's cleanup may execute, but `invoke()` is async and `.catch(() => {})` swallows errors.
3. The IPC message has to round-trip to Rust and Rust has to write the file before the process dies. It races. The process wins. Scrollback never makes it to disk.

Net effect: every time you Quit-from-tray (or rebooted), your scrollback was lost — even though the grid layout, projects, and PTY cwds all came back fine via the synchronous localStorage path.

## What changed

Moved scrollback ownership from the React unmount handler into the **Rust PTY reader thread** (`pty.rs`). The reader thread now writes every output chunk to `data/terminals/scrollback/<tabId>.txt` as it streams — same thread that emits the bytes to xterm.js. No IPC round-trip, no async race.

- New `ScrollbackWriter` struct owns the file for a session's lifetime.
- Tail-truncation: when the file exceeds 200 KB, rewrite to keep the last 100 KB, aligned to the first newline after the cut so partial ANSI escape sequences don't strand across the boundary. Atomic via tmp + rename.
- `pty_spawn` takes a new optional `tabId` parameter. If omitted, behavior is unchanged (no Rust-side persistence). The renderer always passes it.
- The old renderer-side `invoke("scrollback_save", ...)` in the unmount cleanup is removed. It would have overwritten the rich byte-level Rust file with a lossy "last 500 lines, newline-split, no ANSI" snapshot on every tab close.

## What you'll see

Open panes. Run `claude` or whatever produces output. Tray → Quit. Relaunch. The panes come back with the same scrollback you had before, including ANSI colors and formatting — same fidelity as the in-memory xterm buffer was showing.

The "─── scrollback restored ───" marker that's been there since v0.1.17 still fires; it just now actually has the right content above it.

## Edge cases handled

- Existing scrollback files from v0.1.28 and earlier still load fine on first launch — they were written in the "last 500 lines newline-joined" format, which xterm renders as plain text. New writes from v0.1.29 use the rich byte format.
- I/O failures inside the reader thread are best-effort and silently swallowed — losing scrollback durability is worse for the pane's correctness than tearing down the PTY reader on a transient write error.
- File size policy is bounded: 200 KB max, truncate to 100 KB. A long-running `tail -f` won't fill your disk.
- File ownership is single-writer (the PTY reader thread). No conflicts with renderer-side code.

## What this does NOT solve

- Reboot survival for the **running shells themselves**. Shells still die on reboot — only their scrollback survives. The full daemon-split architecture for true alive-across-reboot lives at `pluto-mind/03 Projects/plutos-terminals/daemon-architecture.md` and is gated on the v0.1.28 launch landing first.
- Multi-window attach to the same session (also daemon-spec).
