# v0.1.30 — scrollback restore actually works now

Follow-up to v0.1.29. The disk persistence shipped in v0.1.29 worked — files were getting written with the right content. But on relaunch, no "─── scrollback restored ───" marker appeared and panes came back empty anyway.

## What was wrong

`scrollback_load` used `fs::read_to_string`, which **requires valid UTF-8** and returns `Err` (then `.ok()` → `None` → JS `null` → marker never fires) the moment the file has any invalid UTF-8 byte.

The v0.1.29 reader thread wrote the raw bytes coming out of the PTY. PowerShell on Windows doesn't default to UTF-8 — its `[Console]::OutputEncoding` is typically CP-1252 or the system codepage. Any non-ASCII output (smart quotes, em-dashes, claude's pretty arrows, ANSI escapes followed by certain bytes) lands as a single byte in the 0x80–0xFF range without proper UTF-8 framing. `read_to_string` choked. Whole file got dropped on load.

Diagnostic that caught it: files on disk were 5–9 KB each with valid timestamps — Rust write side was fine, the load side was rejecting them.

## What changed

Two-line fix:

1. **Reader thread writes the lossy-decoded bytes** instead of raw bytes. The xterm emit path was already doing `String::from_utf8_lossy(&buf[..n]).into_owned()` for the event payload. Now the file gets the bytes of that same lossy string, which is always valid UTF-8 (with U+FFFD replacements for bad bytes — exactly what xterm.js shows during live output).

2. **`scrollback_load` is now tolerant of invalid UTF-8.** Read raw bytes, lossy-decode. Existing v0.1.29 files (which have raw bytes on disk) still load — invalid bytes render as U+FFFD, matching what xterm would have shown live.

## What you'll see

Same as the v0.1.29 promise: open panes, run output-producing commands, tray → Quit, relaunch, scrollback comes back with the "─── scrollback restored ───" marker above the live shell prompt.

The U+FFFD substitution is invisible for normal output (Claude's text, git output, ls output — all clean ASCII or proper UTF-8). It only matters for the rare PowerShell-CP1252 stray bytes that were silently breaking the previous load.
