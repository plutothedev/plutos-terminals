# Performance

Audit of plutos-terminals @ `731afc5`, 2026-08-21.

## Summary

The React render-containment work from the P1–P4 plans is genuinely holding at HEAD: all six chrome components are still `memo()`'d, and , the part that actually matters , the prop chain feeding them is identity-stable end to end (every `useWorkspaceTree` mutation is `useCallback([persist])`, `persist` is `[save]`, `save` is `[flushNow]`, `flushNow` is `[]`; the tab maps go through `useStableMap`; `activeTab` is a `find()` into the live state tree rather than a fresh object). The per-PTY-chunk path is disciplined too: activity flips route through a per-pane subscription store with cached snapshots, the cost scan is rAF-coalesced, the Rust side coalesces at 8 ms / 64 KB with a hard 4 MB pending cap, and I confirmed against pinned tauri 2.11.0 source that a second window costs nothing per chunk. The 8/14 findings I was asked to re-verify (H7, M1, M3, and the downgraded M2) are all still in force. Where this surface actually breaks is off the terminal hot path: the two file-browser docks render whole directory listings with no virtualization and no display cap, and the backend cap behind them was raised 10x on 8/16 without anyone touching the renderer. The cost-telemetry surface has a separate defect , the model-family latch can never resolve to anything but Opus, so the dollar figure in the status bar is inflated ~5-17x for Sonnet/Haiku sessions and `/cost` provably cannot correct it downward. The remaining debt is smaller: the SFTP dock does a full SSH handshake on every tab switch, and one rAF coalescer that was applied to the sticky-block scroll path was not applied to its sibling in the prompt editor.

- The activity-store containment is sound: per-pane keyed subscriptions, version-cached map snapshot, and a content-diffed rollup snapshot that keeps identity when a non-indexed split child flips (activityStore.js:139-172). renderContainment.test.jsx pins the identity contract with real hook renders, including the assertion that an unrelated panel does not re-render on a flip.

I read the pinned tauri 2.11.0 source: emit_js_filter (event/listener.rs) looks up js_event_listeners[webview.label()][event] and skips any webview with no registered handler for that event name, so a detached secondary window costs nothing per pty:// chunk despite the broadcast-shaped emit at pty.rs:106-108.

The default dock tab is "files", so the poll is off entirely for most sessions.

- The Rust PTY hot path is well bounded: 8 ms / 64 KB coalescing with a 4 MB pending cap that drops whole-buffer and counts the loss rather than growing unbounded (coalesce.rs:118-125), pooled append handles for transcripts (commands.rs:1330-1376), constant-time scrollback segment rotation that never re-reads the file on the reader thread (pty.rs:592-598), and a single persistent append handle instead of open/write/close per chunk.

## Findings (5)

### HIGH PERF-1, File-browser docks render whole directory listings unvirtualized; the backend cap was raised 5k -> 50k on 8/16 without touching the renderer

`src/features/terminals/LocalFileBrowser.jsx:189`

**What.** `LocalFileBrowser.jsx:189` renders `entries.map((e) => (...))` with no windowing, no display cap, and no `slice()`. Each row is a `div.phn-sftp-row` containing `span.glyph > FileIcon` (an inline `<svg>` with 1-2 `<path>` children), plus `span.name`, `span.size`, `span.mod` , roughly 8 elements per row, and `FileIcon` runs `fileColor()` (`LocalFileBrowser.jsx:60-72`, five regexes) per entry per render. `entries` comes straight from `invoke("list_directory")` at `LocalFileBrowser.jsx:112`, and the backend cap is `LIST_DIRECTORY_MAX: usize = 50_000` (`src-tauri/src/commands.rs:2308`). That constant was `5_000` until commit `c5ff4e8` (2026-08-16) raised it 10x , the commit message's own justification is "C:\Windows\System32 is ~5k by itself, as are large Downloads / node_modules / Maildir trees" , and nothing on the render side changed to absorb it. `package.json` has no virtualization dependency of any kind. `SftpBrowser.jsx:277` is the identical shape for remote listings, and `sftp_list` (`src-tauri/src/sftp.rs:411-417`) applies no cap at all, so a remote directory is unbounded. The Files dock is the DEFAULT right-dock content (`dockTab` initialises to `"files"` in `TerminalsTab.jsx`, and the non-SSH branch renders `LocalFileBrowser`), so this is one double-click away from a cold start, not a corner of the UI.

**Failure.** Open the app (right dock defaults to Files), click Home, double-click into C:\Windows\System32 (~5,000 entries) or a WinSxS/node_modules-scale folder (capped at 50,000). React commits up to ~400,000 DOM nodes plus 50,000 inline SVGs in one synchronous pass, and runs `fileColor`'s five regexes 50,000 times. The window locks for seconds, the resident DOM stays in memory for the life of the dock, and every subsequent re-render of that dock reconciles the whole list. On the SFTP side the same click against a remote maildir or log directory has no cap at all , the listing is also stashed whole into the module-level `listingCache` (SftpBrowser.jsx:19) keyed per (session, path), so browsing N large directories keeps N full listings alive until disconnect.

**Fix.** Cap what is rendered independently of what is fetched: render `entries.slice(0, DISPLAY_MAX)` (a few hundred) with the existing amber `truncated` banner reused to say "showing first N of M", or window the list. The banner copy at LocalFileBrowser.jsx:176-179 already exists for the fetch cap and can carry the render cap too. Same change at SftpBrowser.jsx:277, and give `sftp_list` a cap so the remote path is bounded at all. Also hoist `fileColor` to a memo keyed by extension so it isn't five regexes per row per render.

### HIGH PERF-2, Cost-estimate model family latches to "opus" on the first output chunk and can never change, so Sonnet/Haiku spend is displayed 5-17x too high and /cost cannot correct it

`src/features/terminals/TerminalPane.jsx:652`

**What.** `detectFamily` (TerminalPane.jsx:234-238) returns `DEFAULT_FAMILY` (= `"opus"`, line 227) when the regex does not match: `if (!m) return DEFAULT_FAMILY;`. It therefore never returns a falsy value. The latch at TerminalPane.jsx:652-655 is `if (!e.counters.family) { const detected = detectFamily(text); if (detected) e.counters.family = detected; }` , the `if (detected)` guard is always true, so `e.counters.family` is written on the *first* `checkCost()` call and, because of the `!e.counters.family` outer guard, is never re-evaluated. `checkCost` is scheduled from `handleChunk` on the first rAF after the very first PTY chunk (TerminalPane.jsx:1458-1463), which for a local shell is the shell's own prompt/welcome output , long before the user ever types `claude`. So the family is pinned to "opus" before any model banner can possibly be in the buffer. The rate lookup at line 657-658 then always resolves `FAMILY_BLENDED_RATE_PER_M.opus` = 12.0 (vs sonnet 2.5, haiku 0.7). Worse, the comment at lines 647-648 claims "Authoritative COST_RE matches above already take priority via the monotonic 'only update if higher' rule" , that is backwards. The COST_RE branch (lines 623-627) only writes when `v > next.cost`, so once the inflated estimate is recorded, a genuine `/cost` line printing the real (lower) figure is discarded. The number is surfaced as spend, not as an estimate: `StatusBar.jsx:71-75` renders `${totalCost.cost.toFixed(2)}` with the tooltip "Aggregate live spend across all sessions", and `Toolbar.jsx:12` shows the same value.

**Failure.** Pick Sonnet (or Haiku) in the model picker, or run `claude --model sonnet` in a tab. As tokens accumulate, the status bar's green dollar figure is computed at Opus's $12/M blended rate instead of Sonnet's $2.50/M , a 4.8x overstatement (17x for Haiku). Then run `/cost` inside the session: Claude prints the true "Total cost: $X.XX", `checkCost` parses it, sees it is lower than the inflated estimate, and drops it. The wrong number is permanent for the life of the pane's registry entry and survives pane moves (family lives on `entry.counters`, TerminalPane.jsx:442-446). With a fleet of agent tabs the aggregate in the status bar and toolbar is inflated by the same factor.

**Fix.** Make the fallback distinguishable from a detection: have `detectFamily` return `null` on no match and let the caller keep `e.counters.family` unset until a real banner match arrives (the `family || DEFAULT_FAMILY` at line 657 already supplies the safe default for the not-yet-detected case, which is exactly what the latch was meant to allow). Separately, track the estimate and the authoritative `/cost` figure as two fields so a real COST_RE match always wins over an estimate rather than losing the max().

### MEDIUM PERF-3, SFTP dock tears down and re-handshakes a full SSH connection on every active-tab change, including switches between two tabs on the same host

`src/features/terminals/hooks/useSftpDock.js:90`

**What.** The binding effect's dep array is `[activeTabId, sshKey, dockTab]` (useSftpDock.js:90). `sshKey` (line 80-82) was deliberately introduced as "a stable connection identity so unrelated re-renders ... don't trigger a reconnect", but `activeTabId` sitting alongside it defeats that for any real tab switch: the id changes on every switch, so the effect re-runs and calls `openSftp(token)` (line 87). `openSftp` unconditionally disconnects the current session and evicts its listing cache first (`useSftpDock.js:30`), then performs a fresh `invoke("sftp_connect", ...)` , a full TCP connect, SSH key exchange and auth , even when `sshKey` is byte-identical to the session that was just torn down. On a keychain-backed session it also pays an extra `invoke("secret_get")` round trip (line 39). Because the old session id is gone, `SftpBrowser`'s per-session listing cache (`SftpBrowser.jsx:19`, keyed `sessionId\0path`) and `homeCache` are both cold for the new id, so the on-connect effect at `SftpBrowser.jsx:116-127` re-resolves `sftp_home` and lists the home directory from scratch.

**Failure.** Two tabs open on the same production box, right dock on Files. Browse into /var/log/nginx on tab A, Ctrl+Tab to tab B, Ctrl+Tab back. Each switch drops the SFTP channel and performs a complete SSH handshake plus auth against the same host, and the browser resets to $HOME with a "Loading..." spinner instead of the directory you were in. The same happens on the very common local-tab -> ssh-tab -> local-tab -> ssh-tab alternation. On a high-latency or MFA-fronted host this is seconds of dead dock per tab switch, and it multiplies the auth load on the server in exactly the many-concurrent-tabs workflow the app targets.

**Fix.** Keep a session per `sshKey` rather than per tab: only tear down and reconnect when `sshKey` actually changes (or when the last tab using that key closes). If the per-tab password really must gate it, cache by `sshKey` and reuse the live session whenever the new tab resolves to the same host/user/port. Dropping `activeTabId` from the dep array and re-deriving the password lookup inside `openSftp` is most of the change.

### MEDIUM PERF-4, Prompt editor repositions on every scrolled line with two forced layouts and a fresh-object setState , the rAF coalescer its sibling scroll path got was never applied here

`src/features/terminals/TerminalPane.jsx:2000`

**What.** While the prompt editor is showing, `TerminalPane.jsx:1996-2003` registers `term.onScroll(reposition)` where `reposition` calls `capturePrompt()` directly, with no coalescing. `capturePrompt` (lines 1951-1975) does two `getBoundingClientRect()` calls (`wrapEl` and the `.xterm-screen` element, lines 1959-1961) , each a forced synchronous layout , and then `setPeRect({...})` at line 1965 with a freshly constructed object every time, so React re-renders `TerminalPane` even when all four values are unchanged. The immediate neighbour in the same file does exactly the opposite: `updateSticky` is rAF-gated at lines 1122-1143 with the explicit comment "xterm fires onScroll once PER SCROLLED LINE ... a flood scrolling hundreds of lines per frame ran it hundreds of times for one paint". The same observation applies verbatim to `reposition`, and `costRafRef`/`stickyRafRef` already exist in this component as the established pattern (lines 454-455).

**Failure.** Turn on the prompt editor (`st.promptEditor`), sit at a shell prompt so `showEditor` is true, and flick the mouse wheel or press Shift+PageUp to scroll back through scrollback. xterm emits one `onScroll` per scrolled line, so a single flick over a few hundred lines runs `capturePrompt` a few hundred times inside one frame: ~600 forced layout flushes and ~300 React re-renders of the pane for a single paint. The editor overlay visibly stutters and the scroll drops frames. Gated behind the beta `promptEditor` flag, which is why it is medium and not high.

**Fix.** Wrap `reposition` in the same rAF gate `updateSticky` uses (reuse a ref, final-state-wins is lossless for an absolutely-positioned overlay), and make `setPeRect` bail when the four numbers are unchanged so an identical measurement does not re-render the pane.

### LOW PERF-5, checkCost rebuilds its 10 KB scan window with Array.unshift, making the per-frame scan quadratic in the number of buffered chunks

`src/features/terminals/TerminalPane.jsx:614`

**What.** `checkCost` walks the scrollback chunk list backwards and builds the scan window with `parts.unshift(chunk)` (TerminalPane.jsx:611-617). `Array.prototype.unshift` shifts every existing element, so assembling a k-chunk window costs O(k^2) element moves rather than O(k). k is the number of buffered chunks needed to reach `COST_SCAN_BYTES` (10 KB), which is set by the coalescer's granularity: `Coalescer::push` leading-edges the raw read whenever the session has been idle >= 8 ms (`src-tauri/src/coalesce.rs:56-59`), so a token-by-token agent stream produces many small chunks rather than few large ones. `checkCost` runs up to once per animation frame per streaming pane (TerminalPane.jsx:1458-1463), so the cost is paid at up to 60 Hz per pane simultaneously across the fleet. I am certain of the mechanism; the magnitude scales with chunk granularity, which I could not measure without running the app , at ~1 KB chunks it is negligible, at ~10-20 byte chunks (a slow token stream) the window is ~500-1000 chunks and the rebuild is ~10^5-10^6 element moves per frame per pane. This is a different mechanism from the 8/14 L4 note, which was about the regex scan itself, not the buffer assembly.

**Failure.** Eight agent tabs streaming LLM output token-by-token (each token arriving >= 8 ms apart, so every one leading-edges as its own chunk). Each pane's 100 KB scrollback holds thousands of small chunks; every animation frame each pane rebuilds a ~1,000-element array via unshift before the regexes even start, on the main thread, in the exact window where xterm is also painting eight terminals.

**Fix.** One-line change: push in reverse order and reverse once at the end (`parts.push(chunk)` in the loop, then `parts.reverse().join("")`), or collect indices and `slice` the chunk array. Both are O(k). Optionally drop the scan to ~2 Hz per pane instead of per-frame, as the 8/14 L4 note already suggested.
