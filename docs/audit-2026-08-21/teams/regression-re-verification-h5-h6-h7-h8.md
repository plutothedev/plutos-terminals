# Regression re-verification , H5 / H6 / H7 / H8

Audit of plutos-terminals @ `731afc5`, 2026-08-21.

## Summary

Three of the four fixes in this batch held cleanly at HEAD and are still doing the job they were written for: H6 (ssh_key_generate is now `pub async fn` + `spawn_blocking`), H7 (all six always-on chrome components are `memo()`'d, and I confirmed none of them read mutable module state during render, so the memo cannot go stale), and H8 (PTY ownership is tagged at spawn-birth for all three transports, untagged on both kill paths and on natural exit, and reaped from a `WindowEvent::Destroyed` handler gated on the real `win-` label prefix, with lock discipline as advertised). H5's actual gate change is also intact , `entryLive()` replaced the per-mount `alive` flag, so the tofu-glyph rebuild does survive a tab-move. But the H5 fix quietly swapped a guarded helper for a raw call: it replaced `safeFit()` with a bare `entry.fit?.fit()`, dropping the zero-size guard that the same file's comment 40 lines above says exists to stop exactly this. That is a new defect the fix introduced. One out-of-batch observation worth passing to whoever owns H8 follow-up: the window-ownership tagging covers only PTY/SSH/serial sessions , `rdp.rs`, `vncclient.rs`, `sftp.rs` and `forward.rs` have no owner concept and are not touched by the Destroyed handler, so a secondary window's RDP/VNC/SFTP/tunnel sessions still orphan on close. That gap predates the fix and is not a regression.

## Findings (1)

### MEDIUM R-H5-1, H5 fix dropped the zero-size guard: fonts.ready now fits a hidden pane, shrinking its xterm to ~11x5 and SIGWINCH-ing the shell

`src/features/terminals/TerminalPane.jsx:1204`

**What.** The H5 fix (commit 2c99c2e) correctly changed the gate from the per-mount `alive` flag to `entryLive()`, but in the same edit it replaced the guarded helper `safeFit()` with a raw `entry.fit?.fit()`. `safeFit` is defined at TerminalPane.jsx:1162-1165 as `if (!alive || !opened || !container.clientWidth || !container.clientHeight) return;` and the comment directly above it (lines 1158-1161) says why: "A hidden tab is display:none (0x0); fitting then clamps the PTY to a tiny width and makes zsh redraw a WRAPPED prompt in the background , the 'wonky prompt on tab switch' bug. Skipping 0-size keeps hidden tabs intact." Line 1204 is now the only unguarded `.fit()` in the file , the other four call sites (831, 842, 1164, 1872) all check `clientWidth && clientHeight` first.

The guard is not redundant, because FitAddon does not bail out on a hidden pane. FitAddon measures `terminal.element.parentElement`, which here is the registry-owned host div created at paneRegistry.js:71-75 with inline `width:100%; height:100%`. Inactive tabs are hidden with `display: "none"` at TerminalPanel.jsx:639. For an element with no layout box, `getComputedStyle` returns the computed value, not the used value , I verified this empirically in Chromium with a DOM replica of this exact nesting (`display:none` tab > pane > host with inline 100%/100%): it returns `height: "100%"`, `width: "100%"`, and `parseInt` yields 100, not NaN and not 0. FitAddon's `proposeDimensions` (node_modules/@xterm/addon-fit/lib/addon-fit.js) does `parseInt(...getPropertyValue("height"))`, so it sees a 100x100 px box and returns roughly `cols = max(2, floor((100 - scrollbarWidth) / cellWidth))`, `rows = max(1, floor(100 / cellHeight))` , about 11 columns by 5 rows at the app's `fontSize: 13` (TerminalPane.jsx:864). `fit()`'s only bail-outs are a missing element and NaN, neither of which fires here, so it calls `terminal.resize(11, 5)`.

That resize fires the `term.onResize` handler at TerminalPane.jsx:1580-1587, which invokes `pty_resize` clamped to `MIN_COLS = 40 / MIN_ROWS = 10` (TerminalPane.jsx:136-137). So xterm's buffer reflows and hard-wraps its 10,000-line scrollback (TerminalPane.jsx:876) at 11 columns while the PTY is simultaneously told the terminal is 40x10 , the two disagree, and the shell paints 40-column output into an 11-column grid.

The reason a hidden pane can reach this code at all is the very race H5 was written about: the handler is registered on first mount for every pane, and `document.fonts.ready` at boot resolves late (the comment at line 1189 says "the packaged app consistently lost that race at boot"). A pane that was never opened is safe (`terminal.element` is null, so `proposeDimensions` returns undefined). A pane that is currently visible is safe (it fits correctly). The unsafe state is opened-then-hidden with the font promise still pending.

**Failure.** Cold-launch the packaged app with a restored workspace, then click a second tab within the first second or so , before the bundled MesloLGS NF finishes loading. The tab you just left is now display:none but its xterm was already opened. Its pending `document.fonts.ready` callback fires, `entry.fit.fit()` runs unguarded, and that pane's xterm is resized to roughly 11 columns by 5 rows while its PTY is resized to the 40x10 floor. The shell (or any full-screen TUI in that tab , vim, htop, less, tmux) receives SIGWINCH and repaints at the wrong width into a hard-wrapped 11-column buffer. Switching back to the tab refits to the true size via the guarded show-path refit at TerminalPane.jsx:1869-1872, so the pane is the right size again, but the prompt has been redrawn wrapped and the output written during the shrink stays mangled in scrollback. Before the H5 fix this could not happen: `safeFit()` returned early on a 0x0 container.

**Fix.** Keep the `entryLive()` gate (that part of H5 is right) and restore the size check on the fit. Inside the fonts.ready callback, measure the entry's current slot rather than the disposed fiber's local `container` , e.g. `const slot = entry.currentSlot; if (slot?.clientWidth && slot?.clientHeight) entry.fit?.fit();` (`currentSlot` is maintained by attachHost at paneRegistry.js:118-126). `clearTextureAtlas()` and the `t.refresh()` are the parts that actually fix the tofu glyphs and neither needs a resize, so the fit can be skipped entirely for a hidden pane , the show-path refit at line 1872 will size it correctly on the next reveal.
