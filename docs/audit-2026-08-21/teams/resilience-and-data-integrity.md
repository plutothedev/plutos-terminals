# Resilience and data integrity

Audit of plutos-terminals @ `731afc5`, 2026-08-21.

## Summary

The write primitives on this codebase are in good shape , tmp+rename is applied consistently, the H2 unique-tmp-suffix fix landed correctly in both write_store and notebook_write_sync, L5's atomic save_text_to_file is real, the C5 recording checkpoint streams to disk and recovers on launch, and the scrollback writer's rotation + in-place-truncate fallback are sound and tested. The debt is not in the primitives; it is in the *wiring* around them. Two independent call sites read/write the per-window state blob at the wrong nesting level (`st.panels` vs the real `st.terminalsState.panels`), which silently destroys a detached tab and renders the scrollback GC's entire keep-set safety exclusion inert , and the unit test for one of them enshrines the wrong shape, which is why it survived a full audit. Separately, the C2 durable-backup fix only recognises a corrupt *string*, not the missing-blob case that C2 itself described, and the boot migrations overwrite the backup ~200 ms later; and the C3 SFTP atomicity fix rests on SFTP-v5 rename flags that libssh2 provably never puts on the wire. The shared user blob (workspaces, themes, keybindings, prompts) still has neither corruption detection nor any backup at all.

## Verified sound (11)

- H2 (notebook/store cross-process tmp race) , the fix holds. `unique_tmp_suffix()` (commands.rs:83-87) is pid+atomic-counter based and is used by `write_store` (commands.rs:97), `notebook_write_sync` (commands.rs:2488-2492) and `save_text_to_file` (commands.rs:505), so concurrent writers degrade to clean last-write-wins on the rename rather than corrupting a shared tmp.
- L5 (atomic save_text_to_file) , holds. commands.rs:497-513 stages a same-directory temp and renames, with remove_file cleanup on rename failure; same-dir guarantees a same-filesystem atomic rename.
- C5 (recording checkpoint) , the streaming crash net is real and correctly ordered: header seeded with reset:true at recording.js:92, 2 s debounced JSONL flushes (recording.js:34-49), tail flushed before the in-memory Map entry is dropped in both stopRecording (recording.js:105-110) and pruneRecordings (recording.js:188-192), and the file deliberately left behind on a cancelled/failed Save (TerminalsTab.jsx:848-853). Only the cross-window listing is wrong (RDI-6).
- C3 local half , `stream_to_file_atomic` (sftp.rs:126-152) is correct: temp, drop the handle before rename, remove the temp on any error, destination untouched. It is covered by a real unit test with a mid-stream FailingReader.
- L2 shared safeParse , the knip 'unused export' lead is a false positive. `safeParse` is consumed inside its own module by `loadJSON` (safeParse.js:27), and `loadJSON` has two real callers, macros.js:6 and ptyBridge.js:11, which is exactly the scope L2 named. The helper's storage-access guard is a genuine improvement over the hand-rolled sites it replaced.
- Scrollback durability core (pty.rs:493-634) , reader-thread-owned, no BufWriter (deliberate, so tray→Quit loses at most one chunk), handle closed before the rotation rename, and a newline-aligned atomic tmp+rename fallback when the rename is blocked. Rotation and clobber semantics are covered by cargo tests at pty.rs:2057-2130.
- UTF-8 chunk-boundary carry (`decode_utf8_stream`, pty.rs:678-700) , correctly carries an incomplete trailing sequence and only falls back to lossy decoding on a genuine mid-buffer error, so multibyte characters straddling a read boundary are not corrupted in either the emit or the scrollback file.
- Notebook write/read serialisation (notebookIo.js:76-108) , the per-name promise queue is correct, including the subtle 'only clear the registry if this write is still the queue tail' guard, and `readNotebook` chains behind any in-flight write so a close→reopen loads post-edit content. The name sanitiser closes the silent gate-reject content-loss class.
- Cloud-sync mass-delete guard (syncState.js:108-118) , a store that reads back empty while the snapshot held live items and the owning store looks unloaded carries the snapshot forward instead of manufacturing fleet-wide delete tombstones. The `stamp = snapshot ? now : 0` first-sync rule is also right: a fresh machine cannot claim its defaults are newer than the fleet's real settings.
- sync_git compaction (`gc_at`, sync_git.rs:174-200+) , the clone→rename→rename swap order keeps the original clone recoverable at every step and only runs immediately after a successful push, so it can never discard state the remote does not already hold.
- RemoteEditor dirty guard (C4) , holds: Escape/backdrop/✕ all route through `requestClose`, which awaits a destructive confirm when dirty (RemoteEditor.jsx:111-121), and the cross-component dirty key is correctly gated on `open` so a discarded buffer does not confirm on every later tab close.

## Findings (7)

### CRITICAL RDI-1, detachTab seeds the new window's state at the wrong nesting level, then closes the source tab , the detached session is destroyed

`src/features/terminals/hooks/useWorkspaceTree.js:300`

**What.** The per-window localStorage blob nests the workspace tree one level down. `persist` writes it as `save(prev => ({ ...prev, terminalsState: next }))` (TerminalsTab.jsx:444) and it is read back as `const state = st?.terminalsState || defaultState()` (TerminalsTab.jsx:72). `detachTab` builds a bare terminals-state object , `const newState = { panels: [...], activePanelId, gridMode, projects }` (useWorkspaceTree.js:300-305), exactly the shape `defaultState()` returns , and writes it as the WHOLE window blob: `localStorage.setItem(stateKey, JSON.stringify(newState))` (useWorkspaceTree.js:307), where `stateKey = getWindowStorageKey(winId)`. The missing `{ terminalsState: … }` wrapper means the new `?w=<winId>` window boots with `st = {panels:[…], activePanelId, gridMode, projects}`, `st.terminalsState` is `undefined`, and TerminalsTab falls through to `defaultState()`. Nothing in App.jsx normalises or migrates a top-level `panels` key (grep for `panels` in App.jsx returns only a comment). Meanwhile `closeTab(panelId, tabId)` at useWorkspaceTree.js:317 removes the tab from the source window and a success toast fires. This has been wrong since detach was introduced (commit ede24c4) and there is no test covering detach.

**Failure.** Right-click a live SSH tab → "Detach to new window". A new window opens showing only a fresh empty Home panel, and the tab is gone from the original window. The toast says 'Detached "prod-db" to a new window.' The tab's label, cwd, saved-session/connection binding and startCommands are unrecoverable unless the source panel happened to have another tab open (only then does closeTab stash it in recentlyClosedRef for Ctrl+Shift+T; if it was the panel's last tab, closePanel runs instead and nothing is stashed).

**Fix.** Wrap the seed: `localStorage.setItem(stateKey, JSON.stringify({ terminalsState: newState }))`. Add a vitest that round-trips detachTab's seed through TerminalsTab's `st?.terminalsState` read so the two levels can never drift again.

### HIGH RDI-2, allOpenTabIds() reads st.panels instead of st.terminalsState.panels , the scrollback GC keep-set is always empty

`src/features/terminals/storageKeys.js:59`

**What.** `allOpenTabIds()` walks every `plutos-terminals:state:v0*` key and does `for (const p of st.panels || [])` (storageKeys.js:59). As established in RDI-1, the persisted shape is `{ terminalsState: { panels: [...] } }`, so `st.panels` is `undefined` on every real blob and the function returns `[]` unconditionally. That array is the sole caller-supplied argument to `scrollback_sweep` (App.jsx:413), which turns it into the `keep` HashSet at commands.rs:1197-1212 and skips deletion only when `keep.contains(&name)` (commands.rs:1180). With an empty set, the entire safety exclusion is inert and the sweep degrades to a pure 30-day mtime reaper over every `*.txt` in the scrollback dir. That is exactly the regression the Rust comment at commands.rs:1206-1210 warns about: "`.old.txt` carries the older half of an open tab's history, and its mtime FREEZES at rotation time , age alone would wrongly reap it on month-old resident sessions … this app lives in the tray for weeks." The unit test that exists to prevent this (storageKeys.test.js:25-26, header comment: "If a future state-shape refactor breaks it, the sweep would regress to deleting a live tab's scrollback") builds its fixtures with the same wrong top-level `{panels: […]}` shape, so it passes while the production path returns nothing.

**Failure.** Leave the app resident in the tray (its documented normal mode , closing the window hides to tray, App.jsx:398-402). A tab that rotated its scrollback more than 30 days ago, or any open-but-idle tab whose `<id>.txt` has not been appended to in 30 days, is swept on the next daily sweep even though the tab is open in front of the user. Rust's Windows OpenOptions sets FILE_SHARE_DELETE, so the delete succeeds under the ScrollbackWriter's live append handle: the tab's history is gone and every subsequent byte is written into an unlinked inode, so the tab silently stops persisting scrollback for the rest of the session.

**Fix.** Read `st.terminalsState?.panels || st.panels || []` (keep the legacy fallback for any blob written by detachTab before RDI-1 is fixed). Rewrite the storageKeys.test.js fixtures to the real `{ terminalsState: { panels: … } }` shape , the current fixtures certify the bug.

### HIGH RDI-3, C2's durable backup is only consulted when the blob is a corrupt string; a MISSING blob skips recovery and the boot migrations overwrite store.json within 200 ms

`src/App.jsx:110`

**What.** `parseWorkspace` (workspaceBoot.js:10-19) sets `corrupt: true` only when `raw` is a non-empty string that fails `JSON.parse`; `null`/`""` return `{state:{}, corrupt:false}` by design. App.jsx:110-112 uses that to arm both `bootCorruptRef` and `mirrorSuspendedRef`, and the recovery effect early-returns on `!bootCorruptRef.current` (App.jsx:245). `read_store` has exactly one caller in the whole frontend (App.jsx:250), so the corrupt-string branch is the only path that ever reads the backup. But the failure C2 named , "WebView2 profile corruption after an unclean shutdown → app opens brand-new/empty" , presents as a *missing* key, not a garbled string: a reset/quarantined/rebuilt EBWebView profile returns `null` from getItem. In that case `corrupt` is false, so (a) no recovery runs and no toast fires, and (b) `mirrorSuspendedRef` stays false, so the mirror at App.jsx:182-186 is live. The two unconditional boot migrations then fire: `oledDefaultMigrated` (App.jsx:333-338) and `mobaDefaultForced` (App.jsx:438-441, guarded only by `if (st?.mobaDefaultForced) return`). Each calls `save(...)`, which schedules `flushNow` on a 200 ms timer, which invokes `write_store` with the near-empty state.

**Failure.** User's WebView2 profile is reset (AV quarantine, profile rebuild, unclean shutdown). App boots with an empty layout and no warning. ~200 ms later store.json , the only durable copy of the panels/tabs/session tree , is atomically replaced with `{"uiLayout":"moba","mobaDefaultForced":true,"oledDefaultMigrated":true}`. The backup that existed specifically for this scenario is destroyed before the user can even notice the layout is gone, so even manual recovery from disk is impossible.

**Fix.** On a boot where localStorage is absent, suspend the mirror and read `read_store` first; if it returns a non-empty object while localStorage held nothing, treat it as a recovery candidate (offer it, or adopt it) instead of assuming first run. Alternatively, never let `write_store` replace a non-empty store.json with a state that has no `terminalsState` , the store write is the last line of defence and should refuse to shrink to nothing without an explicit reset signal.

### HIGH RDI-4, SFTP atomic overwrite depends on RenameFlags that libssh2 never transmits , the C3 fix turned a rare truncation risk into a deterministic failure on the common overwrite path

`src-tauri/src/sftp.rs:240`

**What.** `do_upload` (sftp.rs:236-244) and `do_write_text` (sftp.rs:194-202) both stage to a sibling temp and then call `sftp.rename(tmp, dest, Some(RenameFlags::OVERWRITE | ATOMIC | NATIVE))`, relying on OVERWRITE to replace an existing destination. Those flags never reach the wire. `ssh2 0.9.6` (Cargo.lock:6659) forwards them to `libssh2_sftp_rename_ex` (ssh2-0.9.6/src/sftp.rs:407-423), and vendored `libssh2-sys 0.3.2` serialises them only under `if(sftp->version >= 5)` (libssh2/src/sftp.c:2925). That branch is unreachable: `LIBSSH2_SFTP_VERSION` is `3` (libssh2/include/libssh2_sftp.h:58), libssh2 advertises 3 in FXP_INIT (sftp.c:874), and it clamps any higher server version back down to 3 (sftp.c:961-965). So every rename this app issues is a bare SFTP-v3 SSH_FXP_RENAME with no flags , and v3 has no overwrite flag at all; the protocol defines rename-onto-an-existing-path as an error (draft-ietf-secsh-filexfer-02 §6.5), which is what OpenSSH's sftp-server implements (link() then unlink(), returning SSH_FX_FAILURE on EEXIST). Before the C3 fix (ff104d0) `do_upload` used `sftp.create(remote)`, which overwrote correctly.

**Failure.** Open the SFTP dock on any OpenSSH host, navigate to a directory that already contains `nginx.conf`, and upload a new `nginx.conf`. The temp `nginx.conf.pluto-<pid>-<n>.tmp~` uploads fully, the rename is rejected, the temp is unlinked and the user gets 'Upload failed: rename remote temp→dest: …' (SftpBrowser.jsx:168-170). The remote file is never updated , uploads can only ever create new filenames. The same applies to every Ctrl+S in the remote editor on a file that already exists (RemoteEditor.jsx:95-96 toasts 'Save failed').

**Fix.** Do not depend on flags libssh2 cannot send. Either use the `posix-rename@openssh.com` extension where the server advertises it, or fall back to `unlink(dest)` + `rename(tmp, dest)` when the flagged rename fails (a one-instant window, still far better than the pre-C3 O_TRUNC-before-write). Add an integration check against a real sftp-server that overwrites an existing file , the current cargo tests only cover the local-FS half (`stream_to_file_atomic`).

### MEDIUM RDI-5, The shared user blob has no corruption detection and no backup, and the boot keychain migration unconditionally overwrites it with the empty fallback

`src/App.jsx:48`

**What.** `readUserState()` (App.jsx:45-53) is the classic silent-reset-to-empty the L2 fix set out to eliminate: any parse failure on `plutos-terminals:user:v0` returns `{}` with no log, no toast and no flag. Unlike the per-window blob, this key has no durable mirror , the `write_store` mirror at App.jsx:182-186 carries only `st`, never `userSt` , and no equivalent of `parseWorkspace`'s corrupt/absent distinction. The blob is then destroyed rather than merely misread: the keychain-migration effect resolves on essentially every boot and calls `writeUserState(merged)` unconditionally at App.jsx:359, where `merged = { ...userSt(={}), providerKeys, anthropicKey }`. The `safeParse`/`loadJSON` helper built for exactly this class (safeParse.js) has only two callers, macros.js:6 and ptyBridge.js:11 , the L2 fix was never extended to the highest-value blob. The ErrorBoundary's own comment (ErrorBoundary.jsx:80-85) names what lives here: 'keybindings, customThemes, savedPrompts, workspaces'.

**Failure.** One garbled write to `plutos-terminals:user:v0` (quota-truncated write, profile hiccup) and the next launch silently reads `{}`. Every saved workspace, custom theme, keybinding remap, saved prompt, the sync config and the master-password hash are gone from memory with no warning , and within the first second the migration effect writes that `{}` back over the corrupt bytes, so the original blob cannot be recovered even by hand. Workspaces are not in the cloud-sync SOURCES list (syncState.js:7-11), so sync is not a backup for them.

**Fix.** Route this read through the same corrupt/absent split `parseWorkspace` uses: on a non-empty raw string that fails to parse, surface a toast and refuse to overwrite the key until the user chooses. Mirror the (secret-stripped) user blob to the Rust store alongside `st` so it has the same durability the layout got from C2.

### MEDIUM RDI-6, Recording crash-recovery runs in every window and can list, save-partial, or discard a recording that is still live in another window

`src/features/terminals/TerminalsTab.jsx:863`

**What.** The inflight-recovery effect (TerminalsTab.jsx:863-897) is gated only on `userSt?.terminalsOnboarded` and a StrictMode ref , there is no `isPrimaryWindow()` guard, unlike the sibling companion/update effects in the same file. It calls `recording_list_inflight`, which enumerates every `*.cast` in `<data>/terminals/recordings-inflight/` (commands.rs:1518-1531) with no liveness filter. A recording that is actively running in another window has already created its inflight file , `startRecording` seeds it with `reset:true` at recording.js:92-94 and appends every 2 s via `flushCheckpoint`. Because each window is a separate JS realm, the recording Map in window A is invisible to window B, so B has no way to tell a live capture from a crash orphan.

**Failure.** Window A is recording a long session. The user opens a second window (Menu → New window). Window B immediately prompts 'An interrupted recording ("rec-tab_xxx") was recovered. Save it now? Cancel discards it.' Choosing Discard calls `recording_discard` → `fs::remove_file` on the live capture's crash-net file (TerminalsTab.jsx:877). Window A keeps recording; its next checkpoint re-creates the file via `.create(true).append(true)` with no asciinema header line, so if the app is then force-killed the 'recovered' cast is headerless and unreadable by asciinema. Choosing Save writes a truncated mid-session cast and then deletes the crash net anyway (TerminalsTab.jsx:889).

**Fix.** Gate the recovery effect on `isPrimaryWindow()`, and have it skip any name currently in `recording.activeTabIds()`. Better: write a liveness marker (pid + window label) beside the inflight file so `recording_list_inflight` can exclude captures owned by a running process.

### LOW RDI-7, Cross-session command history is a whole-array last-write-wins blob per window , a second window silently drops the first's entries

`src/features/terminals/ptyBridge.js:137`

**What.** `cmdHistory` is a module-level array hydrated exactly once at import (ptyBridge.js:124-129), and `recordCommand` re-serialises the entire in-memory array on every captured command: `localStorage.setItem(HISTORY_KEY, JSON.stringify(cmdHistory))` (ptyBridge.js:137). Each window is its own JS realm with its own copy, and nothing re-reads the key or listens for the `storage` event, so the two copies diverge from the moment the second window loads and every write clobbers the other's additions. This is the same LWW class M10 fixed for `userSt` via `_fieldMeta`, never applied here.

**Failure.** Open two windows. Run `kubectl apply -f prod.yaml` in window A , it lands in the persisted history. Run `ls` in window B; B rewrites the key from its own pre-A snapshot and A's command is gone from persistent history. Ctrl+R search after a restart cannot find it, and the loss is silent.

**Fix.** Re-read and merge before writing (load the key, union move-to-front with the in-memory list, cap, then write), or subscribe to the `storage` event for HISTORY_KEY and merge incoming updates the way the userSt handler does at App.jsx:377-395.
