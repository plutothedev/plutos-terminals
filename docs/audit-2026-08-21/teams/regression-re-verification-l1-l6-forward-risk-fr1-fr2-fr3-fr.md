# Regression re-verification (L1–L6 + forward-risk FR1/FR2/FR3/FR5/FR6/FR8)

Audit of plutos-terminals @ `731afc5`, 2026-08-21.

## Summary

The L-batch held better than the previous waves: L1's AbortController pattern, L2's shared safeParse/loadJSON, L3's lock_recover mirroring across sftp/forward/rdp/vnc/companion, and L4's rAF coalescing are all present and correct at HEAD, and L6's tie-break is genuinely symmetric (I traced both merge orderings by hand). Three residues survive at LOW: a third drag handler (ProjectSidebar) never got the L1 treatment, the SYS mutex in sysstats.rs is the one lock in the file the C1 fix rewrote that still fails to a misleading 0 instead of recovering, and the L5 atomic-write fix now litters a stray tmp file in the user's chosen folder when the write itself fails. On forward risk: FR3's signed updater actually landed and is wired correctly (fail-closed on an empty pubkey, both macOS arch keys emitted, the release job now fails on a missing platform), but its Windows install path exits via std::process::exit(0), which bypasses every exit handler this app registered , including the kill_all that H8 was fixed to guarantee. FR5 was resolved properly (Linux cut AND the underlying keyring-mock bug fixed in Cargo.toml, not just hidden), FR6 is a real gate with prod deps clean, and FR2's name contract is currently clean by measurement even though no test enforces it. FR8 is the one that got worse and it has already fired: two live surfaces render near-white hardcoded text on a themed light background and are literally unreadable in the theme pluto uses daily.

## Findings (6)

### MEDIUM RV-1, UpdateBanner text is invisible in every light theme (hardcoded #E6E6E6 on a themed surface) , the surface the signed updater just made load-bearing

`src/components/UpdateBanner.jsx:175`

**What.** The banner paints `background: "var(--phn-surface-bg, #181818)"` (UpdateBanner.jsx:169) but sets `color: FG_ACTIVE` (line 175) where `FG_ACTIVE = "#E6E6E6"` is a raw hex constant (line 17). `--phn-surface-bg` is `#ececec` under `[data-phn-skin="moba-light"]` (src/features/terminals/headerSkins.css:972) and `#f5f5f7` under `[data-phn-skin="daylight"]` (headerSkins.css:881). The attribute is set on `<html>` (headerSkins.js:366 `document.documentElement.dataset.phnSkin = id`), so the fixed-position banner mounted in App.jsx:479/492 inherits it. #E6E6E6 on #ececec is a contrast ratio of ~1.06:1 , the text is the background. This is not new hex, but commit c507e00 rewrote this component (+71 lines: an Install button, an installing state, an error row) without touching FG_ACTIVE, so the signed-updater work expanded an unreadable surface rather than fixing it. Memory note on file: moba-light is pluto's daily driver.

**Failure.** A user on the Light or Daylight skin gets a released security/bugfix build. The banner appears bottom-right as a bordered box containing, visually, nothing , 'Pluto's Terminal v0.6.2 is out (you're on v0.6.1)' renders #E6E6E6 on #ececec. The two buttons are readable (they have their own backgrounds) but carry no explanation, so the user either ignores the box or dismisses it. The update notice , now the only channel that delivers a fix to an installed copy , is silently unreadable for light-theme users.

**Fix.** Replace `const FG_ACTIVE = "#E6E6E6"` with `var(--phn-text-active, #E6E6E6)` and the dismiss button's `color: "#9D9D9D"` (line 222) with `var(--phn-text-fg, ...)`. The border/accent `#7c9cf5` should become `var(--phn-link, #7c9cf5)` in the same pass , it sits at ~2.8:1 on #ececec.

`src/features/terminals/ProjectDialog.jsx:290`

**What.** The dialog card sets `background: BG` where `BG = "var(--phn-surface-bg, #181818)"` (ProjectDialog.jsx:6) and correctly themes its body text with `color: FG` = `var(--phn-text-fg, #CCCCCC)` (line 8, applied at line 285). ### MEDIUM RV-3, The new signed updater's Windows install path exits via process::exit(0), bypassing kill_all and the window-state save

`src/components/UpdateBanner.jsx:140`

**What.** The app kills PTY children in exactly one place: `if let tauri::RunEvent::ExitRequested { .. } = event { pty::kill_all(...) }` (src-tauri/src/lib.rs:379-384), documented at lib.rs:6 as 'Only an explicit Quit from the tray menu fires RunEvent::ExitRequested -> kill_all() so no shell children orphan'. UpdateBanner.jsx:140 calls `pluginUpdate.downloadAndInstall()`. On Windows that reaches tauri-plugin-updater-2.10.1/src/updater.rs:787-865, whose last statement is `std::process::exit(0)` (line 865). The only hook it runs first is `on_before_exit`, which the plugin wires to `app_handle.cleanup_before_exit()` (plugin lib.rs:107-110) , and that function only clears tray icons, clears resource tables and hides windows (tauri-2.11.3/src/app.rs:1108-1120). It does not emit RunEvent::ExitRequested, does not touch Tauri-managed state, and process::exit runs no Drop impls, so neither `kill_all` nor `impl Drop for PtySession` (pty.rs:407-416) executes. The same miss hits tauri-plugin-window-state 2.4.1, which caches geometry on CloseRequested (plugin lib.rs:447-454) but writes it to disk only on `RunEvent::Exit` (plugin lib.rs:503-504) , and this app's main window prevents close and hides instead (lib.rs:242-247), so RunEvent::Exit is its only disk-write path. The code comment at UpdateBanner.jsx:141-144 shows the team knew about the process::exit; the exit-handler consequence was not followed through.

**Failure.** User resizes/maximizes the window and has several live shells open, then clicks 'Install & restart'. (1) Window geometry: the window-state plugin never reaches RunEvent::Exit, so nothing is written; when the MSI's AUTOLAUNCHAPP relaunches the app it comes back at the geometry from the last clean tray-Quit, or the default. Every update silently resets the user's window layout. (2) Sessions: the deliberate kill + bounded 2s reap in pty::kill_all (pty.rs:1749-1798) never runs and no Drop fires, so shells are left entirely to ConPTY teardown, and SSH sessions get an abrupt socket death instead of the orderly sender-drop channel close the design relies on (pty.rs:418-431) , from the remote host's side an update is indistinguishable from a crash. This is the same orphan-shell class H8 was fixed to close, reopened through a new door.

**Fix.** Do the teardown before handing off: in `onInstall`, invoke a small Rust command that calls `pty::kill_all` and `app.save_window_state(StateFlags::all())` and awaits it, then call `downloadAndInstall()`. Alternatively build the updater in Rust with `UpdaterBuilder::on_before_exit` chained to do both, so the JS path inherits it.

### LOW RV-5, L3's lock_recover was not applied to the SYS mutex in the file the C1 fix rewrote , a poisoned SYS reports 0% CPU / 0 MB memory forever

`src-tauri/src/sysstats.rs:86`

**What.** The L3 fix mirrored pty.rs's `lock_recover` across every registry the audit named (sftp.rs:350/394/548, forward.rs:432/463/515/527, rdp.rs:207/544/579/597, vncclient.rs:207/308/325/338, companion.rs:648/721/794/807/820 , all verified `.unwrap_or_else(|poisoned| poisoned.into_inner())`). sysstats.rs is the file the C1 disk-mutex fix rewrote, and it applies poison recovery to `LAST_DISK_PCT` explicitly, with a comment saying so: `.lock().unwrap_or_else(|e| e.into_inner())` at lines 46-49 and 58-61. Two functions later, the `SYS` mutex that guards the CPU/memory refresh is left non-recovering: `let (cpu, mem_used, mem_total) = match sys_mutex.lock() { Ok(mut sys) => {...}, Err(_) => (0.0, 0, 0) };` (lines 86-98). Poison is permanent for the process lifetime, and the error arm returns values that look like real readings rather than an error.

**Failure.** If any thread ever panics inside the SYS critical section (`sys.refresh_cpu_usage()` / `refresh_memory()` in sysinfo, called from spawn_blocking), the mutex poisons permanently. From that point every status-bar poll in every window, plus the phone companion's stats endpoint, reports CPU 0.0% and memory 0/0 for the rest of the session. Because the fallback is a plausible number rather than an error, the user reads it as an idle machine, not a broken readout , the exact 'misleads a user' shape, and the same permanent-poison behavior L3 asked to be removed.

**Fix.** `let mut sys = sys_mutex.lock().unwrap_or_else(|p| p.into_inner());` matching last_disk_pct/store_disk_pct twenty lines above. (Two other residues are the same class but fail closed rather than misleading: rdp.rs:528 and vncclient.rs:241/285 use `.lock().map(|mut s| s.remove(&id))`, so a poisoned registry silently skips the dead-session removal.)

### LOW RV-6, The L5 atomic-write fix leaves a stray tmp file in the user's chosen folder when the write fails

`src-tauri/src/commands.rs:508`

**What.** L5's fix is present and does the right thing for the failure it targeted: `save_text_to_file` now writes `<chosen name>.tmp-<pid>-<seq>` as a same-directory sibling and renames it over the target (commands.rs:499-513), so a crash mid-write can no longer truncate the file the user picked to overwrite. But the two error paths are asymmetric. The rename failure cleans up , `fs::rename(&tmp, &path).map_err(|e| { let _ = fs::remove_file(&tmp); e.to_string() })?` (lines 509-512) , while the write failure does not: `fs::write(&tmp, contents).map_err(|e| e.to_string())?` (line 508) propagates with the partially-written tmp still on disk. Before this fix a failed save left either nothing or a truncated file at the path the user named; now it leaves an extra file at a path the user never chose and the error message never mentions. `write_store` (commands.rs:98) has the identical asymmetry, though its tmp lands in the app data dir rather than in front of the user.

**Failure.** Save a large transcript or recording to a nearly-full volume (or a folder that goes read-only, or a network share that drops mid-write). The picker resolves, `fs::write` fails partway, and the user gets an error naming the file they chose. Sitting next to it in their Documents folder is a partial `session-2026-08-21.txt.tmp-14328-3` they were never told about and have no reason to look for , repeated across retries, one per attempt.

**Fix.** Wrap the write the same way as the rename: `fs::write(&tmp, contents).map_err(|e| { let _ = fs::remove_file(&tmp); e.to_string() })?`. Apply the same to write_store at commands.rs:98.
