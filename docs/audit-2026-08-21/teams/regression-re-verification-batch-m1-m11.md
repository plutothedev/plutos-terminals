## Summary

Ten of the eleven M-batch fixes held intact at 731afc5, including through the four later commits that re-touched the same files (c5ff4e8, 7b2b8e0, cac924f, a0f363a) , I traced each one to live code rather than to its commit. ## Findings (1)

### MEDIUM M11-R1, M11 quota toast only covers the workspace blob; the user-state blob it names still fails silently under an affirmative success toast

`src/App.jsx:73`

**What.** M11's fix added a one-time quota toast to `flushNow`, the writer for the per-window workspace blob (App.jsx:165-173). The app has a second, independent localStorage writer , `writeUserState` (App.jsx:62-75) , whose catch is still console-only: `console.warn("Pluto's Terminal: user-state localStorage write failed", err)` at App.jsx:73, unchanged from before the audit. That writer owns `USER_STORAGE_KEY`, which holds `workspaces`, `customThemes`, `keybindings`, `savedPrompts`, `welcomeDone` and `terminalsOnboarded`. The fix's own toast copy at App.jsx:171 reads "Trim custom themes or saved workspaces" , both of those fields live exclusively in the untoasted path, not in the blob the toast actually guards. localStorage quota is per-origin and shared across keys, so the blob most likely to trip it (a saved-workspace snapshot is a full deep-copied panel/tab/split tree, `useWorkspaces.js:17`) is written by the path with no user-facing signal. Worse, two call sites report success unconditionally after `saveUser` returns: `useWorkspaces.js:23` fires `toast.success(`Workspace "${name}" saved.`)` and `ThemesSection.jsx:63` fires `toast.success("Imported & applied …")`, neither of which can observe the swallowed write. `setUserSt` still succeeds, so the UI also renders the new workspace/theme as present for the rest of the session.

**Failure.** User with a large workspace (many tabs/splits, several saved workspaces, imported themes) has localStorage at quota. They click Save Workspace and name it "trading". `saveUser` -> `writeUserState` -> `localStorage.setItem` throws QuotaExceededError; App.jsx:73 logs it to a console the packaged build has no devtools for. `useWorkspaces.js:23` then shows a green toast: 'Workspace "trading" saved.' The workspace appears in the list for the rest of the session. On the next launch it does not exist, and no toast ever fired. The same sequence loses an imported Warp theme (ThemesSection.jsx:60/63) and silently reverts keybinding remaps (KeybindingsSection.jsx:37/45).

**Fix.** Extract the one-shot quota warning out of `flushNow` into a shared helper and call it from `writeUserState`'s catch (App.jsx:72-74) as well, sharing the same `quotaWarnedRef` latch so the user still sees at most one toast. Retarget the toast copy to name the data that actually failed, and have `writeUserState` return a boolean so `useWorkspaces.saveWorkspace` and `ThemesSection.doImport` can suppress their success toasts on a failed persist rather than confirming a write that did not happen.
