# Rust backend, IPC and concurrency

Audit of plutos-terminals @ `731afc5`, 2026-08-21.

## Summary

The Rust surface is in genuinely good shape: the 8/14 findings are fixed and verified (disk mutex now try_lock + 2s timeout, SFTP transfers are tmp+rename, H8 window-ownership tags are dropped on every exit path), the 211 `.unwrap()` calls are almost entirely test code or poison-recovering `lock_recover`, and the JS↔Rust IPC contract is clean , I mechanically diffed all 104 registered commands against all 163 `invoke()` call sites and found zero unknown commands and zero camelCase/snake_case arg mismatches. The debt has moved to the edges that prior passes did not reach: code that writes files the app does not own, code that trusts a third-party C parser's error handling, and one sync command that shells out on the UI thread. Two of the six findings (known_hosts rewrite, SFTP mode loss) are collateral damage from correct-looking fixes , the atomic-write pattern was applied without accounting for what a rename destroys.

## Findings (6)

### CRITICAL R1, verify_host_key destructively rewrites the user's shared ~/.ssh/known_hosts from a partial parse, deleting entries and disabling MITM detection for them

`src-tauri/src/pty.rs:1291`

**What.** On every first-seen SSH host, `verify_host_key` loads the user's real `~/.ssh/known_hosts` into libssh2 (`pty.rs:1273`, `let _ = known.read_file(...)` , result discarded), appends the new key (`:1286`), then rewrites the WHOLE FILE with `let _ = known.write_file(&kh_path, ...)` (`:1291`) , result also discarded. Both discarded results hide two libssh2 behaviours I confirmed by reading the vendored C source (libssh2-sys 0.3.2, `libssh2/src/knownhost.c`): (1) `libssh2_knownhost_readfile` reads with `char buf[4092]` via `fgets` and **`break`s out of the read loop on the first line it cannot parse**, so nothing below that line is ever in memory; a known_hosts line longer than 4091 bytes is split by fgets and its tail fragment (pure base64, no whitespace) hits the `if(!*cp || !len)` "Failed to parse known_hosts line" branch, triggering exactly that break. (2) `libssh2_knownhost_writefile` opens with `FOPEN_WRITETEXT` (= "wt" on Windows, the primary target) , truncate-then-write with no tmp+rename , and `break`s on the first writeline/fwrite error, leaving the file partially written. Comment lines and blank lines are also never stored by `libssh2_knownhost_readline` and so are deleted on every rewrite. This is the app performing a non-atomic full rewrite of a file it does not own and that the OpenSSH client shares.

**Failure.** User's `~/.ssh/known_hosts` contains one line libssh2 cannot parse (e.g. an over-long entry, a truncated line, a hashed line whose salt fails base64 decode). User connects from Pluto's Terminal to any host not already pinned. The NotFound branch fires, `write_file` truncates the file and writes back only the entries libssh2 managed to read before it broke. Every entry below that line is permanently gone: `ssh` on the command line now treats those hosts as first-seen, and Pluto's Terminal itself will silently accept-new them too , so an active MITM against any of those hosts is pinned as trusted instead of hitting the `HOST KEY MISMATCH` refusal at `:1277`. Both `write_file`'s and `read_file`'s errors are discarded, so nothing is surfaced.

**Fix.** Do not let libssh2 own the user's file. Keep the app's pins in its own store (the pattern `rdp.rs:150-158` already uses for `rdp-known-hosts.txt`: read, compare, append one line), or if known_hosts must stay canonical, append the single new line yourself with `OpenOptions::append` instead of calling `write_file`. At minimum: check `read_file`'s return (a negative value means the parse aborted) and refuse to rewrite when it did, and stop discarding `write_file`'s error.

### HIGH R2, ssh_key_generate accepts a key name ending in .pub, so the private key lands at a *.pub path that the key manager then displays and copies as "public key"

`src-tauri/src/sshconfig.rs:364`

**What.** `ssh_key_generate_sync` sanitizes the name to alphanumerics plus `- _ .` (`:311-314`) , a trailing `.pub` survives , and passes `-f ~/.ssh/<name>` to ssh-keygen (`:340-341`), which writes the PRIVATE key to that exact path. For name `work.pub`, the private key is written to `~/.ssh/work.pub` and the real public key to `~/.ssh/work.pub.pub`. Line 364 then reads back `path.with_extension("pub")` , which for `~/.ssh/work.pub` resolves to the same path , and returns the PRIVATE key text as `SshKey.public_key`. `ssh_keys_list` (`:222`) compounds it: it treats every `*.pub` file in ~/.ssh as a public key and returns its full contents as `public_key` (`:225`), so `work.pub` is listed forever with the private key in that field. The frontend renders it (`src/features/terminals/SshKeysModal.jsx:98`) and the "Copy public key" button copies it to the clipboard with the toast "paste into the server's ~/.ssh/authorized_keys" (`SshKeysModal.jsx:36-38`). The `path.exists()` guard at `:321` does not stop this because `work.pub` does not exist yet. The same `with_extension` bug also silently returns an EMPTY public key for any dotted name that does not end in `.pub` (e.g. `id_ed25519.work` → reads `id_ed25519.pub`).

**Failure.** User opens SSH keys → Generate new key → types `work.pub` (or `server1.pub`) in the name field → Generate. The app reports success. The key list now shows an entry named `work.pub` whose body is the OpenSSH private key, with a "Copy public key" button. The user clicks it and pastes the private key into a remote server's authorized_keys, a chat, or a web form , following the app's own toast instruction.

**Fix.** Reject a name whose sanitized form ends in `.pub` (and reject `.` entirely, matching the constraint `with_extension` actually imposes). Build the public path as `PathBuf::from(format!("{}.pub", path.display()))`, never `with_extension`. In `ssh_keys_list`, skip a `*.pub` file whose first token is not a recognised key type (`ssh-*` / `ecdsa-*` / `sk-*`) so a mis-created file can never be surfaced as a public key.

### HIGH R3, SFTP save/upload replaces the destination inode, silently widening a restricted remote file from 0600 to 0644

`src-tauri/src/sftp.rs:189`

**What.** The C3 fix converted both write paths to tmp+rename. `do_write_text` creates the staging file with `sftp.create(Path::new(&tmp))` (`:188-189`) and `do_upload` does the same (`:217-218`). `ssh2::Sftp::create` is hard-coded to mode `0o644` (verified in ssh2-0.9.6 `src/sftp.rs:213-220`), and there is no `setstat`/`stat`-then-restore anywhere in sftp.rs , I grepped: the only `stat` call is the 8 MB size check at `:165`. `sftp.rename` with OVERWRITE replaces the destination's inode, so after a save the file carries the temp's 0644 (masked by the sftp-server's umask), not the original's mode. The original's ACLs and extended attributes go with it. The same applies locally: `stream_to_file_atomic` uses `fs::File::create(&tmp)` (`:128`) then renames over `dest`, so a downloaded 0600 remote file lands at the local default mode.

**Failure.** User opens the SFTP browser on a shared server, edits `~/.env` or `~/.aws/credentials` or `/etc/app/secrets.conf` (mode 0600) in the remote editor, hits Ctrl+S. The save succeeds with no warning. The file is now mode 0644 , world-readable to every other account on that host. Nothing in the UI indicates the permissions changed, and the user has no reason to check.

**Fix.** `sftp.stat(remote)` before staging; after the rename, `sftp.setstat(remote, FileStat { perm: original.perm, ..Default::default() })`. Better: create the temp with the captured mode via `sftp.open_mode(tmp, WRITE|TRUNCATE|CREATE, orig_perm, OpenType::File)` instead of `create`, so the file is never briefly 0644 on disk. Mirror the same capture/restore in `stream_to_file_atomic` for the local side.

### HIGH R4, companion_start/companion_stop are sync commands that block the UI event loop on up to four untimed `tailscale` subprocesses

`src-tauri/src/companion.rs:762`

**What.** `companion_start` (`:762`) and `companion_stop` (`:772`) are non-`async` `#[tauri::command]`s. I confirmed against the pinned macro source (tauri-macros 2.6.3, `src/command/wrapper.rs:157-159` and `body_blocking` at `:404-434`) that a command without `asyncness` takes `ExecutionContext::Blocking` and its body runs INLINE in the IPC handler on the main event-loop thread , the same mechanism the 8/14 audit's H6 verified for `ssh_key_generate` (which was fixed; these were not). `companion_start` → `start()` (`:643`) → `ensure_serve(port)` (`:706`) which runs `tailscale serve --bg <port>` with `.output()` (`:134-138`) , a blocking wait on a child process with **no timeout** , then `magic_dns_name()` (`:707`) running `tailscale status --json` `.output()` (`:113-116`), and on its `None` path `best_host()` running `tailscale ip -4` `.output()` (`:82-85`). `companion_stop` → `stop()` (`:724`) → `serve_off()` → a fourth `.output()` (`:153-156`). The file's own comment at `:65` acknowledges "starting and stopping the phone companion runs four of these" , they were made window-less, not moved off the UI thread.

**Failure.** User has Tailscale installed and taps the phone-companion toggle while `tailscaled` is starting up, reauthenticating, or wedged (a known Tailscale state). `tailscale serve --bg` blocks on the LocalAPI and never returns. `Command::output()` has no timeout, so the entire window , every tab, pane, keystroke, and the tray , is frozen with no error and no recovery but killing the app. Even in the healthy case, three sequential process spawns on Windows freeze the UI for a few hundred milliseconds per toggle.

**Fix.** Make both `pub async fn` and wrap the bodies in `tauri::async_runtime::spawn_blocking`, matching the H6 fix at `sshconfig.rs:293-303`. Independently, bound every `tailscale` call: spawn + `wait_timeout` (or `spawn_blocking` + `tokio::time::timeout` around a `.wait()`), treating expiry as "Tailscale unavailable" and falling through to `best_host()`.

### HIGH R5, Companion event relay pushes PTY output into an unbounded channel with no backpressure , a slow phone grows desktop RSS without limit

`src-tauri/src/companion.rs:387`

**What.** `handle_socket` creates `tokio::sync::mpsc::unbounded_channel::<String>()` at `:387`; a single task drains it into the WebSocket at `:389-395`, and `ws_tx.send(...).await` pends whenever the client's TCP receive window is full. The producer side has no bound: the `subscribe` handler registers `ctx.app.listen(channel, ...)` at `:464` whose callback does `tx.send(format!(...))` at `:466-470` for EVERY relayed `pty://` frame. There is no cap on queue depth, no `try_send`, and no drop policy. The `MAX_SUBS = 64` cap at `:400` bounds the number of channels, not the bytes per channel. The coalescer bounds the pending buffer per session (`coalesce.rs:31-33`) but not total throughput , every byte the PTY reads is still emitted, so the queue grows at PTY read rate minus WS drain rate. The `while let Some(Ok(msg)) = ws_rx.next().await` read loop at `:405` cannot break the cycle either: a phone that has stopped reading is also not sending, so the loop stays parked and the listeners stay registered until TCP keepalive fires (2h default).

**Failure.** User pairs their phone, opens a session on the companion page (which subscribes to `pty://<id>`), then locks the phone / walks out of tailnet range / backgrounds the tab, and on the desktop runs something noisy , `cat` a large log, a verbose build, `find /`. The socket stalls, the sender task blocks in `ws_tx.send().await`, and every emitted chunk keeps queueing as a JSON-escaped `String` in the desktop process. A gigabyte of terminal output becomes well over a gigabyte of resident memory in Pluto's Terminal, with no cap and no error, until the desktop app OOMs.

**Fix.** Use a bounded channel (`mpsc::channel(N)`), and in the `app.listen` callback use `try_send` , on `Full`, drop the frame and set a "frames dropped" flag that the sender task flushes as one marker message when it drains. That is the same drop-and-notify shape `Coalescer::enforce_cap` and the SSH 4 MB outbound cap already use. Additionally, put a timeout on the first (auth) frame read at `:373-377`, which currently lets an unauthenticated connection hold a socket and task forever.

### MEDIUM R6, Port-forward / SOCKS proxy tears down the connection on a client half-close, discarding the server's response

`src-tauri/src/forward.rs:162`

**What.** `finished()` at `:161-163` retires a proxied connection when `p.tcp_eof && p.to_ch.is_empty()`. `tcp_eof` is set by `pump` at `:90` on `Ok(0)` from `p.tcp.read(buf)` , which on a TCP socket means the local client sent FIN on its WRITE half only (`shutdown(SHUT_WR)`), not that the connection is over. In the same `pump` call the `to_ch → channel` loop at `:103-119` drains the buffered request, so `to_ch` is empty immediately; the caller at `:210-216` (and `:379-386` for SOCKS) then sees `finished()` true, calls `ch.close()` and `swap_remove`s the proxy before the remote has even replied. There is no `send_eof()` anywhere in the file , I grepped: the only EOF reference is `p.ch.eof()` at `:127`. OpenSSH's own `-L` tracks the two directions independently and only closes when both are done; this does not.

**Failure.** User starts a local forward (or SOCKS proxy) to a service, then runs any client that half-closes to signal end-of-request , Python `sock.sendall(req); sock.shutdown(socket.SHUT_WR); sock.recv(...)`, Java `Socket.shutdownOutput()`, Go `TCPConn.CloseWrite()`, `nc -N`. The request reaches the server, but the tunnel drops the connection the instant the FIN arrives, so the client reads zero bytes and reports a closed connection. The same request works through `ssh -L`. Browsers do not half-close, which is why the SOCKS path looks fine in normal use.

**Fix.** Add a `tcp_read_done` flag distinct from teardown: on `Ok(0)` from the TCP read, drain `to_ch` then call `ch.send_eof()` once and stop reading that direction, but keep pumping channel→tcp. Retire the proxy only when the channel is also at EOF and `to_tcp` is drained , i.e. `finished()` becomes `(tcp_read_done && ch_eof && to_ch.is_empty() && to_tcp.is_empty()) || hard_error`.
