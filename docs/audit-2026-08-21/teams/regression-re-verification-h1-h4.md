# Regression re-verification (H1–H4)

Audit of plutos-terminals @ `731afc5`, 2026-08-21.

## Summary

All four fixes are physically present at HEAD and none were moved or reverted by the 50 intervening commits , I traced each fix commit forward and confirmed later commits (c5ff4e8 hardening, cac924f right-click paste, 45b71d1 L1 drag cleanup) did not touch the fix regions. H1 is the strongest of the four: the nonce gate is correct, its ordering is provably safe, and I found no leak or false-reject path. H3 and H4 close their core failure modes but each leaves an edge the fix's own comment claims is closed. H2 is the weak one: the commit fixed the tmp-file corruption half of the finding and explicitly wrote off the silent-revert half, which was the part the 2026-08-03 fix had originally closed , that data-loss path is still open at the window boundary. The debt is concentrated where a fix designed for one shape (a pane, a single JS context) was applied to a different shape (a modal, a second window).

## Verified sound (12)

- H1 nonce gate , FULLY INTACT and correct. TerminalPane.jsx:1075-1079 mints a 64-bit crypto nonce once per persistent entry; TerminalPane.jsx:1102-1105 splits `PlutoCmd=<nonce>:<b64>` on the first ':' and returns early (swallowed, never recorded) unless `reportNonce === entry.oscNonce`. A missing ':' yields reportNonce "" which also rejects. Base64 contains no ':' so the separator cannot be spoofed by payload content.
- H1 ordering , provably safe, not luck. The nonce mint (TerminalPane.jsx:1075) and the shell-init injection that consumes it (TerminalPane.jsx:1718 buildPosixShellInit, :1735 buildPowerShellInit) are both inside the single effect that opens at TerminalPane.jsx:672, and everything after the re-attach early-return at TerminalPane.jsx:807 is first-mount-only. The mint therefore always precedes the spawn IIFE, so `buildPosixShellInit()` can never be called with the empty-string default (which would have made the gate reject every legitimate report and silently kill command history).
- H1 injection scope , the nonce reaches only local shells. The shell-init block is gated `if (!connection && !serial && cmdsAtSpawn.length === 0 && entryLive() && ptyId)` (TerminalPane.jsx:1674), so it is never written into an SSH or serial stream. shellIntegration.js:56-57 and :85 bake the nonce into the emit for zsh/bash/PSReadLine respectively, and the nonce is a shell-function body, never exported to the environment , a remote host in a nested `ssh` session cannot read it.
- H1 fix region untouched since the fix. `git log 5a329bc..HEAD -- TerminalPane.jsx shellIntegration.js` returns only cac924f (right-click paste), 59bfc02 (canvas renderer) and 0cb6dbd (WebLinks opener); I read the current OSC-1337 handler and it is byte-equivalent to the fix.
- H2 tmp-corruption half , intact for both writers. commands.rs:97 (`store.json.{unique_tmp_suffix()}`) and commands.rs:2490 both derive a private tmp path from pid + a process-wide AtomicU64 (commands.rs:82-86), so two windows or two instances can no longer clobber each other's half-written tmp. Both call sites clean up the tmp on a failed rename (commands.rs:99-102, :2493-2497). Region untouched by the later c5ff4e8 hardening sweep.
- store.json cross-window race , closed at the JS layer, independently of the tmp fix. App.jsx:184 gates the durable mirror on `isPrimaryWindow()` (storageKeys.js:41-43), so secondary `?w=` windows never write store.json at all.
- H3 core , destroyAll blast radius is genuinely gone for the wrapped surfaces. PaneBoundary's componentDidCatch (ErrorBoundary.jsx:30-33) logs and nothing else, with the explicit `// Deliberately NO destroyAll` at :32; only the top-level boundary still calls it (ErrorBoundary.jsx:72). A render throw in VncView, RdpView, NotebookView or RemoteEditor no longer kills every other pane's live SSH/serial/PTY session.
- H3 , the notebook unmount flush survives a boundary catch. When PaneBoundary unmounts NotebookView, React still runs its cleanup (NotebookView.jsx:348-359), so a dirty notebook is still flushed through noteWrite; the fix does not trade one data-loss path for another.
- H3 , the third surface the finding named, custom-theme CSS, is safe by hardening rather than by a boundary. applyActiveTheme (headerSkins.js:464-486) is total over arbitrary cloud-synced JSON: findCustomTheme rejects non-strings (:390), setCustomThemeCss filters keys and values through SAFE_CSS_VALUE (:450-458), and `Object.entries(chrome || {})` cannot throw on a scalar. No throw path found.
- H4 core , the approval promise cannot hang on any modal-dismiss path. agentLoop.js:30 checks `shouldStop()` synchronously immediately before `needsApproval`/`await requestApproval(call)` at :32-33, with no await between, so requestClose (AgentMode.jsx:203-208) either finds a live approveRef and resolves it "stop", or the loop has not yet entered requestApproval and will see stopRef on its next check. There is no interleaving window.
- H4 , the soft-lock the reopen gate could have created is owned. The runningRef gate at AgentMode.jsx:68 skips the reset while a stale loop is in flight, and the try/catch/finally at AgentMode.jsx:170-184 guarantees `setRunning(false)` even when runAgentLoop or the requestApproval executor throws, so Agent Mode cannot become permanently un-startable. The one unbounded await inside the loop, runAndCapture, self-resolves on a 120s timer (ptyBridge.js:272, :284-288).
- H4 fix region untouched since 6b016f3 , `git log 6b016f3..HEAD -- AgentMode.jsx` is empty.

## Findings (3)

### MEDIUM H2-R1, H2 fix closed only the corruption half , cross-window notebook edits still silently revert

`src-tauri/src/commands.rs:2490`

**What.** The H2 fix (commit 1cf50d1) replaced the shared `<name>.md.tmp` with a per-write unique suffix: `tmp_name.push(format!(".{}", unique_tmp_suffix()))` at commands.rs:2490, backed by `unique_tmp_suffix()` at commands.rs:83-86 (`format!("tmp-{}-{n}", std::process::id())`). Its own comment at commands.rs:80-81 states the design intent: "concurrent writes degrade to clean last-write-wins on the atomic rename instead of corrupting." That closes the tmp-clobbering half of finding H2. It does not close the other half the finding named , "last rename wins, silently reverting the other's edits , the exact class the 8/03 single-process fix closed, reopened at the window/process boundary." The recommended fix was "OS-level advisory lock / lock-file keyed by target path in the Rust write commands"; there is none. `notebook_write_sync` (commands.rs:2472-2498) takes no lock, does no mtime/version check, and unconditionally renames the caller's full content over the target. The JS serializer that would have ordered the writes is still module-scoped to one webview: `const inflightWrites = new Map()` at notebookIo.js:68. Secondary windows are separate webview contexts (spawn_new_window, commands.rs:447; per-window state keys, storageKeys.js:34-36) while the notebooks directory is global, so two windows each hold their own empty `inflightWrites`. NotebookView writes whole-file snapshots , `const snapshot = contentRef.current` (NotebookView.jsx:223) then `await noteWrite(name, snapshot)` (NotebookView.jsx:229) on a 2s autosave, plus a fire-and-forget flush on unmount (NotebookView.jsx:351-356). Nothing reconciles against what is on disk.

**Failure.** Open notebook "notes.md" in the main window. Menu > New window (MenuBar.jsx:83), open the same "notes.md" there. Type a paragraph in window 2 and wait 2s (autosave lands). Type a different paragraph in window 1 and wait 2s. Window 1's write renames its own full snapshot , which never contained window 2's paragraph , over the file. Window 2's editor still shows its text and reports "Saved", but the paragraph is gone from disk and is lost the moment window 2 reloads or is closed. No error, no conflict prompt, no toast. Same outcome with two app instances (there is no single-instance guard: no `single_instance` in Cargo.toml or lib.rs).

**Fix.** Make the write conditional rather than blind: have `notebook_write` take the content hash or mtime the client last read, compare it under the write, and return a distinct `conflict` error when the on-disk file changed underneath. NotebookView then surfaces "this notebook changed in another window" instead of overwriting. An advisory lock keyed by target path (the finding's original recommendation) serializes the writes but does not by itself stop the stale-snapshot overwrite, so the compare-and-swap is the load-bearing part.

### MEDIUM H4-R1, H4's "a closed Agent Mode is a stopped Agent Mode" is false on the lock-screen path , unmount does not set stopRef

`src/features/terminals/AgentMode.jsx:203`

**What.** The H4 fix wires the modal's dismiss paths to the stop path: `requestClose` at AgentMode.jsx:203-209 sets `stopRef.current = true` and resolves any pending approval with "stop" before calling `onClose()`, and it is passed as `<Modal ... onClose={requestClose}>` at AgentMode.jsx:212. That is correct and I verified it cannot leave a hung promise (see clean list). But the fix is implemented entirely in the close handler; AgentMode has no unmount cleanup that stops the loop , its three effects (AgentMode.jsx:59, 60-70, 71) return nothing. The component is unmounted, not merely hidden, whenever App swaps to the lock screen: `if (welcomeDone && lockHash && !unlocked) { return <LockScreen .../> }` at App.jsx:464-466, with `destroyAll()` fired at App.jsx:460-462. That gate is reachable mid-session because `lockHash` is derived live from `userSt.masterPasswordHash` (App.jsx:455), MasterPasswordModal sets that hash via `saveUser((prev) => ({ ...prev, masterPasswordHash: hash }))` (MasterPasswordModal.jsx:28), and it never calls `markUnlocked()` , so `unlocked`, seeded from the sessionStorage flag (App.jsx:138, masterPassword.js:62-63), is still false on a session that never saw a lock screen. The orphaned `start()` closure keeps running: `shouldStop` reads a ref on a dead component that nothing will ever set, so the loop keeps calling `toolTurn` (agentLoop.js:17) and, under auto-run, keeps executing read-only MCP tools through `invoke("mcp_call_tool", ...)` (AgentMode.jsx:141) , a path with no dependency on the destroyed panes. The comment at App.jsx:457-459 shows the lock was specifically designed to stop unsupervised auto-approval behind the password gate ("a parked PTY behind the password gate could keep auto-approving with zero supervision"); the agent loop escapes exactly that guarantee.

**Failure.** Start an Agent Mode run with auto-run enabled. While the model is mid-turn, open Settings and set a master password for the first time. App immediately renders LockScreen and calls destroyAll(). AgentMode unmounts; stopRef is never set. Behind the lock screen the loop continues for up to MAX_STEPS (14, agentLoop.js:11) further LLM round-trips on the user's API key and keeps firing auto-run MCP tool calls with no visible approval UI. If the loop reaches an approval-gated call, `requestApproval` (AgentMode.jsx:149) sets state on the unmounted component and its promise never settles, stranding the closure for the life of the process. Unlocking remounts AgentMode fresh (running=false), so the orphan is invisible in the UI.

**Fix.** Give AgentMode the same teardown its close path has: `useEffect(() => () => { stopRef.current = true; if (approveRef.current) resolveApproval("stop"); }, [])`. Unmount and close then share one stop path, so the invariant in the AgentMode.jsx:198-202 comment actually holds. (Separately worth a look outside this batch: setting a master password mid-session immediately destroys every live session via App.jsx:460-462 and locks the user out of a password they just created, because MasterPasswordModal never marks the session unlocked.)

### LOW H3-R1, PaneBoundary applied to a modal child renders an undismissible non-modal fallback and strands the owner's open-state

`src/features/terminals/chrome/ModalHost.jsx:168`

**What.** PaneBoundary (ErrorBoundary.jsx:22-53) is written for a pane: it catches locally, deliberately skips destroyAll (ErrorBoundary.jsx:32), and renders an inline `<div style={{ padding: 16, ... }}>` fallback whose only control is "Try again" (ErrorBoundary.jsx:34-51). Three of its five call sites are genuine panes (TerminalPanel.jsx:644 VNC, :646 RDP, :648 Notebook) and that is correct. Two wrap modals/overlays instead: ModalHost.jsx:168-175 (DiffView) and SftpBrowser.jsx:308-316 (RemoteEditor). DiffView renders a `<Modal>` (DiffView.jsx:76-78); the boundary's fallback does not, so on catch the overlay is replaced by a plain block in normal flow inside TerminalsTab's page container (ModalHost is rendered at TerminalsTab.jsx:1253, inside the `.phn-page` div opened at :1027). It has no close control and Escape does nothing, because Modal is gone. The owning state is also stranded: `diffWorktree` lives in TerminalsTab (TerminalsTab.jsx:110) and the only `setDiffWorktree(null)` outside DiffView's own `onClose` is inside the worktree-discard success path (TerminalsTab.jsx:505), which is itself reached only from the crashed component. TerminalsTab never unmounts during normal use, so the stranded state and its fallback block persist. "Try again" (ErrorBoundary.jsx:46) only clears `error` and re-renders the same DiffView, which throws again for any deterministic render fault. Note also that the `tries` counter it increments is never consumed , there is no key bump, contrary to the comment at ErrorBoundary.jsx:20-21; the remount happens only because the subtree was unmounted while the fallback showed.

**Failure.** With an agent worktree open for review, any render-time throw inside DiffView (a `git_diff` payload shape the renderer does not expect, a bad worktree object) trips the boundary. The modal vanishes and is replaced by a permanent 'Diff view hit an error. / Your other sessions are unaffected.' block wedged into the terminal chrome. There is no way to dismiss it: Escape is dead, there is no ✕, and 'Try again' immediately re-throws. The user must reload the window , which is the outcome PaneBoundary exists to avoid , and the sessions the fix saved are then killed by the reload anyway.

**Fix.** Give PaneBoundary an optional `onDismiss` and render the fallback inside the same Modal shell when the wrapped child is a modal, so Escape/✕ clear the owner state (`setDiffWorktree(null)` / `setEditTarget(null)`) and the boundary resets. Alternatively move the boundary outside the conditional and have it call the owner's close handler from componentDidCatch. Also drop the unused `tries` state or actually key the children with it so the comment matches the code.
