## Stream A: Agent rules + codebase context

**Goal:** the native agent (AgentMode) stops flying blind. It reads project rule files and cheap project facts before its first turn, the way Warp/Cursor agents do.

### Architecture

New pure module `src/features/terminals/agentContext.js` (unit-testable, no React):

- `collectProjectContext({ cwd, invoke })` (single injected Tauri dispatcher; testable with fakes) walks from the pane cwd up to the git root (max 12 levels; **max 3 levels when no git root is found**, so unrelated ancestor rule files don't bleed in) and collects:
  - **Rule files:** `AGENTS.md` and `CLAUDE.md` at each level. Injection order root -> cwd so nearer files win by recency in the prompt. Both names collected; nothing else (no `.cursorrules`, YAGNI). **Symlinked rule files are skipped** (never read). Rust-side walk stops early once collected bytes exceed 32 KiB.
  - **Project facts:** cwd, git branch + dirty flag (the existing `git_branch_status` command returns `{branch, dirty}`; no per-type counts exist and none are fabricated), top-level directory listing (names only, max 60 entries), npm scripts if present (package.json name deliberately omitted; cwd already conveys it).
- **Cap:** 16 KB combined budget. Rule files get priority over facts; oldest (root-most) rule content truncates first, each truncation marked `[...truncated]`.
- All filesystem/git access goes through injected functions backed by existing Tauri commands. No new Rust unless a needed primitive is missing; if one is (e.g. bounded upward file probe), it lands in `commands.rs` as a narrow async command per house rules.

**Global user rules:** free-text field in Settings -> AI ("Rules"). Stored in `userSt` (NOT keychain; it is not a secret), so it rides existing cloud sync. Injected before project rule files.

**Rule-file trust gate (TOFU, plan-audit addition):** a rule file's content injects ONLY after a one-time user approval of that exact content (per-path content hash stored in `userSt.approvedRuleFiles`). First sight (or any content change) puts the file in a "pending review" state: the run proceeds WITHOUT it, the context chip shows pending files, and the user approves from the chip preview after seeing the exact text. This is the real control against link-swapped rule files (a hardlinked `AGENTS.md` pointing at a key file cannot be detected by metadata; showing the content to the user before anything leaves the machine can). Symlinks are additionally skipped at the Rust layer. The user's own global Rules text needs no approval (user-typed).

**Secret scan (plan-audit addition):** `secretScan.js` is built in Stream A as a shared pure module (AWS/GitHub/OpenAI/Anthropic/Slack key shapes, PEM headers, JWTs). The assembled context block is scanned before injection; hits are masked in the text sent to the LLM and warned in the chip. Stream D reuses this module for gist sharing.

**Injection point:** AgentMode builds its system prompt today; the context block is **appended after the instruction text** each run (instructions first, context after; deliberate deviation from this spec's earlier "prepended" wording, declared 2026-07-21). Fresh collection per run, no caching across runs. The block is clearly delimited: `## Project context (auto-collected)`.

**Prompt-injection posture (honest statement):** rule files are DATA in the system prompt in the same trust tier as tool results. The shell approval gate in `agentTools.js` stays code-side and cannot be widened by prompt content (`isDangerousCommand` + MCP annotations decide; both verified untouched). Residual risk stated plainly: (1) with auto-run ON, tools whose MCP servers declare them read-only can be driven by injected text without a human click; (2) `isDangerousCommand` is a denylist, so a non-matching but harmful shell command shows in the approval box without the red warning. The TOFU gate reduces both by making every injected rule file user-reviewed content, and the disclaimer line in the block is framing only, not a control.

**UI:** a small chip row in the AgentMode panel showing what loaded ("rules - AGENTS.md (2) - CLAUDE.md - git facts") with a click-to-expand preview of the exact injected text. Settings toggle "Inject project context" (default ON) and the chip reflects OFF state.

### Error handling

Missing files, unreadable dirs, non-git cwd, SSH/serial panes (no local cwd): each degrades silently to whatever subset is available; empty context = no block injected, chip shows "context: none". Collection failure never blocks the agent run (collected inside try/catch; catch means no block).

### Testing

Unit tests on `agentContext.js` with fake fs/git: precedence order, cap + truncation marker, non-git fallback, SSH-pane fallback (collector receives `cwd: null`), budget split. Existing `agentLoop.test.js` untouched (loop API unchanged).

## Stream B: Debt burn-down (#29, #27, #25), in that order

### B1 (#29): moveTab must not kill the PTY

**Today:** `moveTab` across panels kills + respawns the session. Only standing violation of invariant 1 (PTYs survive React).

**Design:** promote pane ownership out of React into a **pane registry** living beside `ptyBridge` (same module family, `src/features/terminals/paneRegistry.js`):

- Registry entry per tab id: `{ xterm, fitAddon, container: HTMLElement, listeners }`. The registry owns the xterm instance and its container div for the pane's lifetime.
- `TerminalPane` becomes a mount shell: on mount it asks the registry for the tab's container and appends it into its DOM slot; on unmount it detaches (does NOT dispose). Dispose happens only on explicit tab close (registry `destroy(tabId)`).
- `moveTab` = tree-state update only. The destination `TerminalPane` mounts, requests the same container, re-appends it (xterm survives DOM re-parenting), calls `fit()` + `scrollToBottom()` + focus restore.
- PTY events already flow through `ptyBridge` keyed by tab id, so the backend session is untouched by any of this.

**Risk points (each gets an explicit test or manual-smoke line):** fit/resize after re-parent, scroll position, listener double-bind on remount, focus restore, close-during-move race (registry destroy wins; mount request for a destroyed id spawns fresh).

### B2 (#27): React subscribes via `useSyncExternalStore`

`ptyBridge`/registry expose store slices (per-tab status, title, exit code, cost counters) with `subscribe(tabId, fn)` + `getSnapshot(tabId)`. Components (TerminalPane header, tab strip badges, cost telemetry consumers) move from ad-hoc event listeners to `useSyncExternalStore`. Kills the leaked-listener / disposed-xterm class (invariant 4) at the subscription layer. Event emission API stays for non-React consumers.

### B3 (#25): TerminalsTab decomposition

Mechanical extraction from the 1,404-line `TerminalsTab.jsx` into `src/features/terminals/chrome/`: `MenuBar`, `Toolbar`, `TabStrip`, `StatusBar`, `FKeyBar`, `CommandPalette`, `ModalHost` (the ~27 modals' mounting), each receiving already-memoized props. Rules:

- One extraction per commit, `npm run build` green + behavior-identical (no new renders: the existing memoization contract from repo CLAUDE.md is the acceptance bar; spot-check with React DevTools profiler on the 2.5s sysstats poll).
- No logic changes ride along with a move. Logic changes (if any are discovered) become separate follow-up commits.

### Testing (stream-wide)

Registry unit tests (attach/detach/destroy/move sequences, close-during-move). `useSyncExternalStore` slice tests (snapshot stability, unsubscribe on unmount). Extraction commits rely on build + existing vitest suite + the manual smoke line-items.

## Stream C: Notebooks + Saved Prompts

### Notebooks (runnable markdown with captured outputs)

**Model:** a notebook is a plain `.md` file on disk. Default dir: `<app-data>/notebooks/`, configurable in Settings. Files stay valid markdown outside the app (git-friendly, durable; pointing the dir at a git repo or synced folder works today). NOTE: the cloud-sync engine merges **fields** across its 3 stores, not files, so notebook files do NOT ride cloud sync in v1; that integration is a recorded follow-up (see Out of scope). Saved Prompts DO sync (they are `userSt` fields).

**New tab type `notebook`** (the workspace tree already supports typed tabs for RDP/VNC/SFTP): Monaco editor (already bundled for DiffView/RemoteEditor) with a rendered preview toggle.

**Runnable blocks:** fenced code blocks with shell languages (`sh`, `bash`, `powershell`, `pwsh`, `cmd`) get a gutter Run button.

- Run sends the block's text to a **target pane** (default: last-focused terminal pane; picker in the notebook toolbar, persisted per notebook in frontmatter).
- **Output capture:** the command is sent wrapped with the existing OSC-133 integration; the capture listens on that pane's `ptyBridge` stream for the command-begin/command-end markers of THAT command and collects output between them. Reuses the agent-mode capture path in `ptyBridge` (the one hardened in v0.5.0 for tab-close). Timeout 120 s, cap 256 KB (matches macro cap precedent), both surfaced in the block on trip.
- Captured output writes back under the block as a fenced block: ` ```output (2026-07-20 14:32, exit 0)` ... ` ``` `. Rerun replaces that block. Manual edits inside an output fence are overwritten on rerun (documented in the notebook template header).
- **No auto-run ever.** Blocks run only on explicit click. Run-all runs sequentially with per-block stop-on-failure.

**Save model:** explicit save (Ctrl+S) + autosave on tab close/app quit, atomic tmp+rename via existing store command patterns.

### Saved Prompts

`{ id, name, body, tags[] }` list in `userSt` (rides cloud sync). UI: a "Prompts" section in the existing Snippets drawer (same interaction grammar, separate list; snippets = shell, prompts = AI). Insert points:

1. Assistant (DockAssistant) input: `/` menu.
2. AgentMode goal input: `/` menu.
3. Prompt editor: `/prompt <fuzzy>` completion inserting the body.

### Error handling

Target pane closed mid-run: capture resolves with what arrived + "(pane closed)" marker, notebook stays consistent. Unwritable notebook dir: toast + tab stays open with in-memory content. Sync conflict on a notebook file: existing sync engine conflict rules apply (no special-casing).

### Testing

Pure-module tests: markdown block parser (find runnable blocks, find/replace owned output fences, never touch user prose), output-fence writer idempotence, capture wrapper (fake ptyBridge: begin/end markers, timeout, cap, pane-close). UI smoke via manual checklist.

## Stream D: Gist block sharing

**Goal:** right-click a command block -> share -> permalink on the clipboard. Community-visible artifact with zero infrastructure.

### Flow

1. Entry points: block context menu ("Share block..."), tab context menu ("Share transcript...").
2. **Preview modal** shows exactly the text that will leave the machine (command + output, or full transcript). Nothing is ever uploaded without this modal confirming.
3. **Secret scan** runs on the preview text, reusing `secretScan.js` built in Stream A: regex set for AWS keys (`AKIA...` + secret pattern), GitHub tokens (`ghp_`, `gho_`, `github_pat_`), OpenAI/Anthropic-style keys (`sk-...`), Slack tokens (`xox.-`), PEM private-key headers, JWTs, and a generic high-entropy hex/base64 run heuristic. Hits are masked in the preview and listed as red warnings. Share button label flips to "Share anyway" when hits exist. Scan is advisory, not blocking (his content, his call), but defaults protect.
4. Visibility: **secret gist default**, public opt-in per share.
5. Auth resolution order: `gh auth token` (if gh CLI present, via existing silent-command pattern) -> PAT stored in OS keychain via existing vault (Settings -> Sharing, one-time paste, `gist` scope only). No token in `userSt`/localStorage, per the keychain rule.
6. Create via GitHub REST (`POST /gists`) from Rust (`share.rs`, async command; secrets never touch argv). Filename `plutos-terminal-share-<date>.md`, content as markdown with a small header (app name + link) for organic attribution.
7. On success: URL to clipboard + toast. Gist id + url + date + title stored in `userSt` share history.
8. **My shares** list (Settings -> Sharing): open in browser, delete (DELETE `/gists/:id`, which revokes the link), remove from history.

### Error handling

No auth available: modal explains both paths (install gh / paste PAT), nothing uploads. API failure: toast with status, modal stays open with content intact. Delete failure on a revoke: history entry marked "delete failed, open on GitHub to remove".

### Testing

Unit: secret-scan corpus (true positives per pattern + benign lookalikes), markdown assembly, auth resolution order with fakes. Rust: share command arg validation, no-shell invocation of gh. Manual: end-to-end share + revoke against a real gist once, during pluto's smoke.

## Cross-cutting build process (per pluto's standing build-loop)

- **Anchor before first commit:** tag `pre-v0.6-buildout-2026-07-20` + branch `backup/pre-v0.6-buildout`. Never rebase / reset --hard / force-push / rewrite history. Forward-only commits.
- Every commit gated on `npm run build` + `cd src-tauri && cargo check` + `npx vitest run` green. Rust changes also `cargo test`.
- Subagent-driven TDD per task; adversarial plan-audit before execution; whole-pipeline audit at the end; **re-review every fix** (non-optional; it has caught a critical or regression in nearly every prior round).
- `git push` and release tagging are pluto's: exact commands handed over at ship time.
- New files carry the `(C)` marker. New blocking Rust commands are `async fn`. Functional `save()` updaters only. UTF-8 boundary carry in any new byte-stream reader.
- Version bump v0.5.0 -> v0.6.0 across `package.json` + `Cargo.toml` + `tauri.conf.json`, `CHANGELOG.md` + `releases/v0.6.0.md`, at the end after the whole-pipeline audit.

## Out of scope (recorded, not forgotten)

- Code-signing decision and the v0.5.0 manual GUI smoke (pluto-only items, still outstanding, unchanged by this build).
- Live multi-viewer session sharing, voice, theme-from-image (roadmap "Later" bucket).
- A pluto-branded share viewer/backend on top of gists (possible v2 of Stream D).
